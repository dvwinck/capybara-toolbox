- **Status:** requirements, UX and design analysed on 2026-10-14; spec written, **awaiting owner review** before the implementation plan.
- **Date:** 2026-10-14
- **Backlog entry:** #4, score 36 (U 4 x A 9), effort M.
- **How it was refined:** twelve scope questions asked one round at a time (three rounds of four), then a design review in chat, then a clickable prototype ([tidy-board-prototype.html](tidy-board-prototype.html)) that was exercised in a browser and corrected twice (see section 7).

## What it is

A new plugin, `tidy-board`, with one skill of the same name. It scans one git repository for branches, worktrees and stashes that look finished, turns each into a card, and deletes only the ones the person approves. The agent never improvises git: a separate `apply` step re-checks every item at the moment of deleting.

The point is safety, not speed. Deleting the wrong thing costs more than leaving clutter, so every card shows its proof, and anything that exists in only one place is backed up before it goes.

## Decisions

| --- | --- | --- |

| T2 | Unmerged work | Listed with an alert and an extra confirmation. Its commits are shown and a backup ref is created first. |
| T3 | Who deletes | A plugin subcommand, `apply`, that re-verifies each approved item and only then deletes. The agent does not run git itself. |
| T4 | Scope | One repository per batch: the current directory or a path argument. |
| T5 | Engine sharing | Separate plugin carrying a **vendored, generated byte copy** of `ar_board.py` (`capy_board.py`), with a byte-equality `--check`. ar-board gains no command that deletes. |
| T6 | Detecting "merged" | Local git plus optional `gh`, with a visible proof level per card (section 3). |
| T7 | Many safe cards | Group by proof; a summary card approves the whole "proved" group; unique work and stashes never go in bulk. |
| T8 | In use or dirty | Never offered. They sit in a "do not touch" block with the reason. |
| T9 | Vocabulary | Own labels **Apagar / Manter / Depois** on the same A/R/M keys, with a danger tone on the destructive action. |
| T10 | Age | No age filter; cards are sorted by safety, then by age. |
| T11 | Recovery | A backup ref for P3 and P4 items only, plus `applied.json` for everything. `restore` brings a backup back. |
| T12 | Card context | Proof plus last commit and ahead/behind; up to 5 unique commits; the PR when `gh` is available; worktree path and size. |
| T13 | Bulk mechanics | A group summary card plus the individual cards (no new panel UI). Rule in 4.3. |

## Rulings made without asking (owner can overturn)

- **R1.** Only local refs are deleted. If a branch has a counterpart on `origin`, the card says so and does not touch it. Cost if wrong: one extra manual `git push --delete`.
- **R2.** Without `gh`, the highest proof is P1. Cost if wrong: some PR-merged branches show as P3 or P4 and need the extra confirmation.
- **R3.** No hard cap on cards, but `check` warns above 40. Cost if wrong: a long board.
- **R4.** "Upstream is gone" is shown as a hint but **never raises the proof level**: a remote branch can be deleted without being merged. (The design summary in chat listed it as a P3 signal; this corrects that.)
- **R5.** The base is `--base`, else the target of `refs/remotes/origin/HEAD`, else the first existing of `main`, `master`, `base`, `trunk`. A branch counts as merged if it is an ancestor of the local base or of `origin/<base>`.

## Out of scope for v1

- Remote branches, tags, and deleting the `origin` counterpart.
- Scanning several repositories in one batch.
- Any scheduled or automatic cleanup. It runs only when the person asks.
- Rewriting history, `git gc`, or pruning objects.

## 1. Job to be done

Agent sessions and worktrees leave branches behind. Months later nobody remembers which ones matter, and the cleanup is a quiet chore that gets postponed because deleting the wrong branch hurts. The person wants to see the candidates, understand how sure the tool is about each, and clear the safe ones quickly without ever risking unmerged work.

## 2. Flow

1. **`scan`** reads the repository (no fetch, no network, read-only) and writes `batch.json` and `scan.json` into `.tidy-board/<batch_id>/`.
2. **`serve`** (the vendored engine, started as a subprocess) shows the board. The person decides.
3. **`apply`** refuses to run unless the decisions file is finished and belongs to this batch and round; then re-verifies and deletes item by item.
4. The agent reads `applied.json` and reports what was deleted, skipped (and why) and backed up.

`batch.json` is a normal ar-board batch, so the existing engine, token, Host check and CSP are reused unchanged. The git facts live in a sidecar, `scan.json`, so the engine schema does not need tidy-board fields.

## 3. Detection and proof levels

| Level | Criterion | Treatment |
| --- | --- | --- |
| P1 | The tip is an ancestor of the base (`git merge-base --is-ancestor`). | Safe. Eligible for the group action. |
| P2 | `gh` reports a merged PR whose head sha equals the branch tip. | Safe. Eligible for the group action. |
| P3 | Every commit's patch-id is present in the base since the merge-base (`git cherry` shows no `+`), **or** the branch's cumulative diff has the same patch-id as one base commit (a squash). Bounded to 500 base commits. | Probable. Extra confirmation and a backup ref. |
| P4 | Anything else: unique work. | Alert, extra confirmation, backup ref. |

- A false negative is safe (the item stays P4 and is protected). The dangerous error is a false positive; P3 therefore never joins a bulk action and always gets a backup.
- Stashes are always P4. They are matched and dropped by commit sha, never by `stash@{n}`, which shifts.
- A worktree card removes the worktree and, when its branch is P1 or P2, the branch as well.
- **Never offered:** the base, the current branch, any branch checked out in a worktree (the worktree is the card), and any worktree with tracked changes or untracked files.

## 4. Data and CLI contract

### 4.1 Files in `.tidy-board/<batch_id>/`

- `batch.json`: ar-board batch with `labels` and per-item `confirm` (section 5). First item is the group card `G`; then items `T01...` sorted P1, P2, P3, P4, and by age inside a level.
- `scan.json`: per item, `{id, kind: branch|worktree|stash, ref, sha, proof, branch?, path?}` plus `base`, `base_sha`, the scan time and whether `gh` was used.
- `decisions.json`: written by the engine, as today.
- `applied.json`: one entry per processed item, `{id, kind, name, sha, action: deleted|skipped, reason?, backup?}`.

### 4.2 Subcommands (stdlib only, `python3 -I`)

- `scan [REPO] [--base REF] [--gh auto|off] [--out DIR]` -> `AR-BOARD`-style summary line and the batch directory. Exit 0.
- `apply DIR [--dry-run]` -> table of actions; exit 0 clean, 1 if any item was skipped, 2 on a refusal (unfinished, wrong round, dirty tree changed the plan).
- `restore DIR ID` -> recreates the branch or stash from `refs/tidy-board/backup/...` and removes that backup ref.
- `check DIR` -> validates `batch.json` and that every item has a `scan.json` entry.

### 4.3 The group card

The first card is a summary, "Delete the N branches proved as merged", listing every P1 and P2 item. It carries no ref of its own. The `apply` rule, which the summary and the review screen mirror:

- A P1/P2 item is deleted when its **own** decision is Apagar, or it has none and the group card is Apagar.
- An own decision of Manter or Depois always wins over the group.
- P3, P4 and stashes ignore the group card entirely.
- No decision means keep. Nothing is ever deleted by default.

### 4.4 `apply` re-verification (per item, at deletion time)

- **Branch:** the ref exists; its tip still equals the scanned sha (otherwise skip: "changed since scan"); it is not the current branch nor checked out; P1 is recomputed. Delete with `git branch -D` only after the checks pass. P3/P4: create `refs/tidy-board/backup/<name>` first; if that fails, skip.
- **Worktree:** the path exists, the tree is clean and HEAD equals the scanned sha; `git worktree remove` **without** `--force`; then its branch per the rule above.
- **Stash:** find the commit sha in `git stash list`; back it up as `refs/tidy-board/backup/stash-<sha7>`; drop by the index found at that moment.
- Nothing runs `--force` on a worktree, touches the network, or edits `origin`.

## 5. Engine changes (ar-board 1.3.0, additive)

Only for boards that ask; existing boards are byte-for-byte unaffected.

1. **`labels`** at the batch level: `{"approve": {"text": "Apagar", "tone": "danger"}, "reject": {"text": "Manter", "tone": "safe"}, "maybe": {"text": "Depois"}}`. The page uses the text on buttons, chips and summaries, and the **tone** decides the colour: with `danger`, the approve action uses the `--no` tokens and reject uses `--ok`. Without tone it behaves as today.
2. **`confirm`** per item (a non-empty string): the first A press arms the card ("press A again to confirm, Esc cancels") and shows the string; only the second A records `approved`. Mouse and keyboard behave the same; moving to another card disarms it.
3. `summary` prints the custom labels; the JSON keeps `approved|rejected|maybe` so nothing downstream changes.

The vendored copy is a plugin-side byte copy of the 1.3.0 engine. `tools/sync.py` of tidy-board generates it and `--check` fails on drift, as the question-board copy does.

## 6. UX

One card at a time, as in the ar-board. The card is organised for a decision in under 30 seconds:

- **Proof pill first**, colour plus text (green P1/P2, amber P3, red P4), never colour alone.
- Title in the serif the page already uses: "Apagar a branch `name`?" / "Remover o worktree ..." / "Descartar ...".
- A box with last commit, ahead/behind, PR, remote note; worktree path and size.
- For P3 the heuristic is explained in one sentence; for P4 a red box lists up to 5 unique commits (or the stash files) and names the backup ref.
- Buttons: **Apagar** (danger), **Manter** (safe), **Depois** (amber); an armed risky card swaps Apagar for a solid **Confirmar: apagar**.
- A collapsed "Nao tocar" block above the card lists what is never offered and why.
- The side panel keeps the comment box, the numbered chips (red, green, amber by decision) and counts that exclude the group card.
- A **review screen** before finishing, in three columns: will delete, will keep, no decision. It names which items get a backup. Nothing has been deleted at that point; "Concluir" only releases `apply`.

## 7. What the design review changed

The prototype was run in a browser and corrected twice before this spec:

- The group card said "P1" although the group mixes P1 and P2, and the counts treated the group card as a deleted item. Both fixed; counts now exclude it.
- The simulated result showed a P3 item deleted with no backup. Since P3 is a heuristic, a false positive would lose unique work silently. **Backup now covers P3 and P4** (decision T11 amended).
- It also surfaced the colour problem: reusing the engine's green for "approve" would paint **delete** as the friendly action, so `labels` carry a tone (section 5).

Not verified: the prototype shows the light theme only, no dark theme render, no 360 px viewport, no screen reader.

## 8. Risks

- **False "merged" (the headline risk).** Mitigated by proof levels, P3/P4 confirmation, the backup ref and the re-check in `apply`. The safe direction of error is always "keep".
- **State changes between scan and apply.** Handled by the sha check; a changed item is skipped and reported, not deleted.
- **Squash detection is a heuristic.** Rebased or conflict-resolved squashes will usually land in P4. Acceptable: they are protected, just more tedious.
- **`refs/tidy-board/backup/*` accumulate** in the repo being cleaned. `restore` removes one; a `--prune-backups` is deliberately not in v1.
- **Rubber-stamping the group action.** The group lists every member and only ever covers P1/P2; a member can still be set to Manter.
- **A plugin that deletes** raises the stakes of every bug. Hence tests against real temporary repositories, the dry run, and no network.

## 9. Test plan

Unit tests only, in the style of publish-check: temporary git repositories assembled at run time.

- **Classification:** each level (ancestor, merged PR via a fake `gh` on PATH, cherry-equivalent, squash patch-id, unique), the never-offered cases (base, current, checked out elsewhere, dirty and untracked worktree), stash identity after other stashes are dropped.
- **Apply:** sha changed after scan -> skipped; unfinished or other-round decisions -> refused; group rule matrix (approved group with an own Manter/Depois/none, P3 under an approved group is untouched); backup created before deletion and `restore` round-trips; `--dry-run` changes nothing; worktree remove never uses `--force`.
- **Engine 1.3.0:** `labels` and `confirm` validation, the armed state on the page (string guards and `node --check`, as today), boards without them unchanged, the generated copy drifting fails `--check`.
- **Documented examples** parse and pass `check`.
- **Manual:** a real browser run, light and dark, and a run against a scratch clone with a squash-merged branch.

## 10. Build order

1. Engine 1.3.0: `labels` with tone and `confirm`, with tests and the changelog; the ar-board suite stays green.
2. Plugin skeleton: manifest, vendored copy and sync `--check`, catalog entry, CI picks up `plugins/*/tests`.
3. `scan`: base detection, classification, `batch.json` and `scan.json`.
4. `apply`, `restore` and `check`, with the safety tests.
5. Skill, example, EN and PT-BR docs, release 0.1.0, one real run on a scratch repository.

## Open doubts

- Whether the P3 patch-id comparison is reliable enough on long-lived bases (the 500-commit bound may miss old squashes; they fall to P4, which is safe).
- Whether `gh` output for a PR whose branch was force-pushed after merge still matches the tip sha (if not, it falls to P3).
